# 厂家能力与按键冲突清单 第一轮

本清单用于决定 `protocol-v1` 应用如何使用头盔硬件，以及以后是否与厂家主应用共存。依据为 `Reference/Node/厂家协议/` 中的《巡检模式 独立应用对接说明》《驱动指令》《对接设备端接口文档》，本仓库代码，以及 2026-10-27 对联调头盔的只读检查。文档中的接口是厂家方案，只有经过设备核对的项目才标为现机可用。

## 现机状态与源码边界

- 设备当前由 `/oem/helmet/helmet_monitor.sh` 启动我们的 `/oem/helmet/helmet`，本地配置 `keyEvent=true`。厂家 `/oem/echo/safety_helmet` 和 `/oem/app/RdCamera`、`asr_worker` 文件存在，但检查时未运行；厂家说明所列本地 `:90` 和 `:11122` 端口未监听。因此目前不能直接调用其拍照、录像或按键切换 HTTP 接口。
- `/oem/echo` 和 `/oem/app` 中检查到的是可执行程序、配置、资源及脚本，未发现 C/C++/Go 源文件。设备固件文件不能替代厂家源码。厂家协议 PDF 描述的是厂家应用与其平台的交互，当前不能据此认为我们的应用已经能读取相同的实时数据。
- 当前已运行的 `protocol-v1` 只完成大模型交互所需的连接、文件受理、语音播放和平台控制；`get_status` 只返回录音、播放、运行时长和应用版本等应用状态，尚未集成下面的厂家硬件数据。

## 能力核对

| 能力 | 厂家资料中的途径 | 现机检查 | 下一步 |
| --- | --- | --- | --- |
| 电量和电压 | I2C 的 `raw_soc`、`voltage_mv` 节点 | 两节点存在且可读 | 确认量纲、异常值及采样频率，再决定是否加入设备状态 |
| 充电状态 | 厂家驱动指令写“待补充”；平台协议有 `charging` 字段 | 无已确认的本地读取路径 | 向厂家确认驱动节点，不能从平台字段反推本机接口 |
| GPS | `/dev/ttyS6`，9600 波特 | 串口节点存在；未打开串口或验证定位数据 | 确认是否有现存进程占用、报文格式和定位条件 |
| 主板温度 | `/dev/lqbp001ta_temp` | 该节点不存在；系统另有 thermal zone | 核对本机固件节点与温度含义，不直接把 SoC 温度当成厂家报警温度 |
| 佩戴、跌落、近电、蓝牙外设等 | 厂家平台上报或报警字段 | 尚未找到已验证的本地驱动或 SDK | 逐项询问厂家硬件装配、驱动节点和读取方式 |
| 拍照、麦克风、扬声器 | 当前应用直接使用设备媒体接口；厂家另描述 `RdCamera` HTTP、Mic SDK 和板端播放命令 | 当前拍照、录音、播放已在我们的链路验收；厂家服务未运行 | 先保留现有实现，若恢复厂家服务须做摄像头、录音和声卡互斥测试 |
| 本地录像 | 厂家方案通过主应用开停录，读取 MP4；当前应用另有 H264 录像路径 | 厂家 HTTP 服务未运行；未验收共存 | 先确定产品是否需要录像，再统一文件格式与按键入口 |
| Wi-Fi 和网络状态 | 厂家平台协议可下发 Wi-Fi；系统另有网络脚本 | 本机网络脚本存在，厂家主应用未运行 | 网络配置与平台控制分开设计，避免未经验证地混用两套指令 |
| 照明灯、激光和指示灯 | sysfs/GPIO | 照明灯和指示灯节点存在；未写入或试灯 | 确认厂家原安全行为后再设计控制权限 |

## 按键冲突

厂家文档把 `/dev/input/event0` 定为电源，`event2` 定为灯、SOS、音量，`event3` 定为对讲和拍照/录像。现机这些 input 节点存在，名称分别与电源和 ADC 按键设备相符。本仓库 `key/key.c` 读取这些节点，现行行为为：

| 按键事件码 | 当前应用行为 | 厂家文档行为 | 结论 |
| --- | --- | --- | --- |
| `116` 电源 | 长按约 4 秒关机 | 电源/关机 | 以后必须明确唯一负责方 |
| `115` 音量 | 循环切换音量 | 调音量 | 语义接近，策略不同 |
| `62` 对讲/录音 | 按住录音，松开上传给大模型 | 对讲录音 | 同键不同业务，需模式或优先级 |
| `61` 拍照 | 松开拍照并上传给大模型 | 拍照；厂家还支持录像键长按切换录像 | 需确定短按、长按是否保留录像 |
| `60` 灯 | 松开切换照明亮度 | 短按照明、长按激光 | 当前缺少长按激光行为 |
| `59` SOS | 按下开始 H264 录像、松开结束 | 紧急呼叫/SOS | **高优先级冲突：不能把当前录像行为当作 SOS 功能交付** |

厂家《巡检模式 独立应用对接说明》提出由主应用提供 `/api/button_control`，切换后独立应用读取 input；文档明确标注该接口“待实现”，语音“切换到巡检模式”词条也是待增加。当前主应用未运行，因此本机不存在已验证的动态模式切换。即便以后恢复厂家应用，也要先验收只由一方处理业务按键，并确认崩溃后如何交还按键；不能仅同时启动两套程序。

## 建议的下一轮工作

1. 先确定产品级按键规则：SOS 必须保留紧急用途还是另有企业安全流程；录音、拍照、录像分别用短按还是长按；电源、音量、照明是否保留厂家默认行为。语音唤醒先核对厂家 ASR 能力与可交付 SDK，不把文档中的可选词条当成现成功能。
2. 向厂家核实这台型号实际装配的传感器、本地读取接口、Mic SDK 与应用共存方案，以及 `/api/button_control` 是否已有可交付版本；若要恢复厂家主应用，取得对应源码/构建方法或明确由厂家维护二进制。
3. 在按键规则和共存方式确定后，先处理 SOS 映射，再做单项硬件读取与互斥测试。只有真实可用且业务需要的数据，才定义设备上报协议；暂不扩展现有大模型交互消息。

本轮仅做只读检查，未启动厂家程序、未修改按键、网络或设备配置。
